# 0.5.1 — Un `git commit -q` que falló no pide anotar el HEAD viejo

- **Fecha**: 2026-11-21 · **Commit**: ver el tag `session-handoff-v0.5.1` · **Tipo**: fix
- **Visto en**: una sesión de Claude Code que hacía commit en un proyecto con hooks de pre-commit

## Síntoma

Un `git commit -q` falló en el hook de pre-commit del proyecto (faltaban dependencias en un worktree nuevo) y el
plugin pidió anotar en `PROGRESS.md` el hash `9883811`, que era el HEAD de `dev` hecho por otra persona, no un
commit de la sesión.

## Causa

Con `-q`, la salida de `git commit` no trae el hash. El plugin lo tomaba de `git log -1` sin comprobar que ese commit
fuera el que acababa de hacerse. Si el commit fallaba, HEAD seguía en el commit anterior y el plugin lo daba por nuevo.

## Cambio

`freshCommit` (en `hooks/handoff.ts`) lee `git log -1 --format=%h %ct` y solo acepta el commit si tiene menos de
`FRESH_COMMIT_SECONDS` (10 min). Aplica en Claude Code (`register.tsx`) y en Codex y Antigravity (`actions.ts`).

## Prueba

- `hooks/handoff.test.ts`: `git log -1 counts as the commit that just ran only while it is fresh`.
- `hooks/register.test.ts`: `a -q commit that failed in a hook does not ask for the old HEAD`.
- `tests/cli/actions.spec.ts`: el mismo caso y `a -q commit that worked asks for its fresh hash`.

## Lección

Un dato que se deduce del estado (HEAD) y no de la salida del comando debe comprobar que el comando lo produjo.
