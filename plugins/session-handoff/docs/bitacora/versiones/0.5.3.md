# 0.5.3 — Un Stop continuado en el mismo turno vuelve a evaluar PROGRESS.md

- **Fecha**: 2026-11-21 · **Commit**: ver el tag `session-handoff-v0.5.3` · **Tipo**: fix
- **Visto en**: una sesión de Codex en Windows que dejó `Phase: external-wait` y siguió bloqueada al cerrar cada turno

## Síntoma

El hook repetía el mismo bloqueo (`Parada 1 de 3 sin cambios en PROGRESS.md`) con el paso anterior de la sesión
(`Phase: implementation`), aunque PROGRESS.md ya decía `Phase: external-wait`. La fase de espera no liberaba y el
tope de paradas nunca se alcanzaba: el agente quedaba en bucle.

## Causa

`stop()` devolvía la respuesta guardada cuando llegaba un Stop con el mismo `turn_id`. Esa idempotencia era para un
Stop entregado dos veces. Codex, en cambio, continúa el mismo turno después de un bloqueo y conserva el `turn_id`:
el bloqueo guardado se repetía sin releer PROGRESS.md ni contar paradas.

## Cambio

- `stop()` reutiliza la respuesta solo si el mismo turno llega dentro de 2 s de la última evaluación
  (`DUPLICATE_STOP_MS`). Si no, la vuelve a evaluar.
- `SessionState.lastStopAt` guarda ese instante. Los estados de versiones anteriores lo leen como `null`.
- `dist/hook.mjs` regenerado.

## Prueba

`tests/cli/actions.spec.ts`: dos casos nuevos. `un Stop continuado en el mismo turno…` comprueba que external-wait
libera después de un bloqueo. `…llega al tope` comprueba que sin cambios en PROGRESS.md la parada se corta. Los dos
fallaron antes del cambio, con el mismo texto que vio la sesión real. Después: `bun test tests/cli` pasa 59 y
`claude plugin test .` pasa 70.

## Lección

Una respuesta idempotente por turno solo es segura si el turno no continúa después de bloquear. El dedupe necesita
una ventana de tiempo, no solo el id del turno.
